# XO Nursery Platform — Cursor AI Rules
# Read this entire file before responding to any prompt.
# Confirm you have read it by stating: 'Rules loaded. Ready to build XO.'

## PROJECT IDENTITY
- Project: XO Nursery Management Platform
- Stack: React 18 + Vite + TailwindCSS + Supabase + TypeScript
- Market: Egypt. Bilingual Arabic (RTL) + English. Arabic is default.
- Builder: Non-developer. Explain what you are doing in plain language.
- Style: shadcn/ui components + Tailwind. Never invent new component styles.

## GOLDEN RULES — NEVER BREAK THESE
1. NEVER hardcode API keys, secrets, or passwords anywhere in code.
2. NEVER use the Supabase service role key on the frontend.
3. NEVER modify or drop database tables directly — always write a migration file.
4. NEVER skip RLS (Row Level Security) on any database table.
5. NEVER move to the next feature until the current one is tested and working.
6. NEVER create a file longer than 300 lines — split into smaller components.
7. NEVER do anything destructive (delete files, drop tables, restructure folders)
   without first explaining what you are about to do and asking for confirmation.
8. NEVER expose camera stream URLs or signed tokens in frontend state or console logs.
9. NEVER store user passwords — always use Supabase Auth.
10. ALWAYS write TypeScript with proper types — never use 'any'.

## ARCHITECTURE RULES
- All four surfaces share one Supabase project and one React codebase.
- Routing: /admin/* /parent/* /teacher/* /xo-admin/*
- Route guards must check BOTH Supabase auth session AND user role from DB.
- All data fetching uses React Query (TanStack Query) — never raw useEffect fetches.
- Global state uses Zustand — activeUser, activeChild, activeBranch, activeNursery.
- All Supabase calls go through /src/lib/supabase.ts — never import supabase client directly elsewhere.
- Edge Functions handle: WhatsApp dispatch, invoice generation, stream tokens, QR validation.
- Never call Supabase service role from client-side code.

## DATABASE RULES
- Every new table MUST have RLS enabled immediately after creation.
- Every RLS policy must be written and tested before any data is inserted.
- All migrations go in /supabase/migrations/ with sequential numbering: 001_, 002_, etc.
- Never ALTER or DROP a table in production without a rollback migration ready.
- All tables include: id (UUID default gen_random_uuid()), created_at, updated_at.
- Foreign keys always have ON DELETE behavior explicitly set.
- All queries must include nursery_id filter — never query across nurseries.
- Indexes must be created for: nursery_id, parent_id, child_id, class_id on all major tables.

## SECURITY RULES
- Environment variables: only VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY on frontend.
- Service role key: only in Supabase Edge Functions, never in React code.
- All file uploads: validate file type and size before uploading. Max 10MB per file.
- Signed URLs for all private storage: 1-hour expiry for media, 30-min for CCTV tokens.
- CCTV stream tokens: generated by Edge Function only, include nursery_id + parent_id + camera_id + expiry.
- All forms: sanitize inputs. Never pass raw user input to SQL queries.
- Auth: session refresh handled automatically by Supabase client. Never store tokens in localStorage manually.
- Content Security Policy headers must be set on all responses.

## UI/UX RULES
- Component library: shadcn/ui ONLY. Never build custom UI primitives.
- Icons: lucide-react ONLY. Never use emoji as UI icons.
- Typography: Inter font (already in Tailwind config). Sizes: text-sm, text-base, text-lg only.
- Colors: use only the XO color palette defined in tailwind.config.ts.
- Loading states: every async operation must show a loading skeleton, not a spinner.
- Error states: every async operation must show a human-readable error message in Arabic and English.
- Empty states: every list or table must have a designed empty state — never show a blank page.
- Mobile-first: all parent and teacher surfaces designed at 375px base. Use Tailwind responsive prefixes.
- RTL: when language is Arabic, apply dir='rtl' to root. Use Tailwind's rtl: prefix for mirrored layouts.
- Forms: all form fields must have labels, placeholder text, and error messages in both AR and EN.
- Confirmation dialogs: all destructive actions (delete, cancel, deactivate) require a confirmation dialog.
- Modals: use shadcn Dialog component. Never use browser alert() or confirm().

## ERROR HANDLING RULES
- All Supabase calls wrapped in try/catch with typed error handling.
- User-facing errors shown in toast notifications (shadcn Sonner) — never console.log only.
- Network errors: show 'Connection issue. Please check your internet and try again.' in AR + EN.
- Auth errors: redirect to /login with a clear message about what happened.
- 404 pages: styled, branded, with a 'Go back' button — never a blank page.
- Loading timeout: if any fetch takes more than 10 seconds, show a timeout message.
- Form validation: run client-side validation before any API call — never submit invalid data.

## ARABIC / RTL RULES
- All text strings go in /src/locales/ar.json and /src/locales/en.json — never hardcode text.
- All UI text uses the t() function from react-i18next — never raw strings in JSX.
- When language = Arabic: dir='rtl' on <html>. Icons that indicate direction must flip.
- Numbers in Arabic mode: use Intl.NumberFormat('ar-EG') for all numeric displays.
- Dates in Arabic mode: use Arabic month names and right-aligned date display.
- All database fields with user-facing names have _ar and _en variants stored separately.
- RTL layout: icons on right side in LTR become left side in RTL. Use Tailwind rtl: prefix.
- Never use absolute pixel positioning for text — it breaks RTL.

## FILE & FOLDER RULES
- /src/components — shared UI components only. One file per component.
- /src/pages/admin — admin portal pages only.
- /src/pages/parent — parent PWA pages only.
- /src/pages/teacher — teacher PWA pages only.
- /src/pages/xo-admin — XO Super Admin pages only.
- /src/pages/auth — all auth flows.
- /src/hooks — custom React hooks. Prefix with 'use'. One hook per file.
- /src/lib — supabase.ts, i18n.ts, utils.ts, webrtc.ts, whatsapp.ts.
- /src/store — Zustand stores. One file per store.
- /src/types — TypeScript types. One file per domain (child.ts, invoice.ts, etc.).
- /supabase/migrations — all DB migrations. Never edit old migration files.
- /supabase/functions — all Edge Functions. One folder per function.
- Max 300 lines per file. If a file exceeds this, split it.

## SESSION RULES
- At the start of each session: read .cursorrules, read PROGRESS.md, state what you will work on.
- At the end of each session: update PROGRESS.md with what was completed and what is next.
- Before starting any new feature: confirm the previous feature is working.
- If you are unsure about a decision: ask the user before proceeding. Do not guess.
- If a prompt is ambiguous: ask one clarifying question before writing code.
- After completing a feature: write a plain-language summary of what was built.

## TESTING RULES
- After each feature: test the happy path, the error path, and the empty state.
- Test on mobile viewport (375px) for parent and teacher surfaces.
- Test RTL layout after every UI component is built.
- Check that RLS is enforced: log in as a parent and confirm you cannot see other parents' data.
- After any DB migration: verify existing data is intact.

## WHAT TO DO WHEN STUCK
- If you hit an error you cannot resolve in 2 attempts: stop and explain the problem in plain language.
- Never silently skip a broken feature and move on.
- Never delete and recreate — fix what is broken.
- If the Supabase schema needs to change: write a new migration, do not edit old ones.
