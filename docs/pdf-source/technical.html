01

Big picture

System overview

XO Platform is a multi-tenant SaaS for nurseries. A single React single-page application serves four role-specific portals. It talks directly to Supabase, where PostgreSQL holds the data, enforces tenant isolation with row-level security (RLS), and runs all money and attendance logic in server functions.

Design principles

The database is the security boundary

Every table that holds tenant data has RLS. The UI hides what a role cannot use, but correctness never depends on the UI. A direct API call with a user's token gets exactly the same answer.

Critical logic runs on the server

Payments, invoice generation, enrollment, attendance and billing run in SECURITY DEFINER PostgreSQL functions called by RPC. They are atomic, locked, idempotent and audited, never a series of client-side inserts.

Thin client, typed data hooks

Pages compose small TanStack Query hooks (src/hooks), one per data concern. Mutations write the result straight into the cache, and Realtime refreshes other screens.

Configuration over code

Nursery behaviour (hours, billing rules, payment methods, media privacy and more) lives in nursery_settings. Roles and feature grants live in database tables, so neither needs a release to change.

Multi-tenancy model

LevelDescription
PlatformOperated by xo_super_admin users, who can reach every nursery.
ChainA group of nurseries (chains). chain_super_admin users are scoped by users.chain_id.
Nursery (tenant)The isolation unit. Almost every table carries nursery_id, and RLS compares it with current_user_nursery_id().

Three request paths

Read

A hook calls supabase.from(table).select(). PostgREST runs the query as the user, and RLS removes every row the user may not see.

Critical write

A hook calls supabase.rpc(fn). The function checks the caller's role and tenant, locks the rows it touches, validates, writes and logs in one transaction.

Live update

Postgres broadcasts the change. RealtimeQuerySync refreshes the matching cached queries, so other users' screens update without a reload.

Data layer

TanStack Query

  • Global defaults: staleTime 5 minutes, gcTime 10 minutes. Volatile hooks override them.
  • After create, update or toggle, mutations write the returned row straight into the cache with setQueryData, so the UI updates instantly without waiting for a refetch.
  • Derived cross-entity values (for example a deal's assigned packages and children) are refreshed by invalidating the related key.

Realtime

  • RealtimeQuerySync subscribes to Postgres changes on the public schema. Realtime applies RLS, so users only receive rows they may read.
  • Bursts of changes are combined into one refresh. Queries on screen refetch immediately, and the rest are marked stale.
  • Application tables with RLS are in the supabase_realtime publication (migration 20261005000000).

The server-function pattern

Logic that moves money or changes attendance is written as a PostgreSQL function and called with supabase.rpc(). Each function follows the same template:

  1. Declared as SECURITY DEFINER with set search_path = public and set row_security = off. It runs with the owner's rights, so it must check permissions itself.
  2. Authenticates the caller through auth.uid() and reads their role, nursery and chain from users. It rejects callers outside the target tenant (42501).
  3. Locks the rows it changes (select … for update) to serialise concurrent requests such as double clicks or two devices.
  4. Validates state and amounts: balance checks, allowed status transitions, and payment already started.
  5. Is idempotent: money actions take an idempotency key, and a retry returns the first result instead of acting twice.
  6. Writes and audits atomically, including audit events and notifications to parents and staff, in one transaction.
  7. Is granted narrowly: internal helpers and cron functions have EXECUTE revoked from anon and authenticated, and only user-facing RPCs are granted.

Roles and permissions

Base roles

The Postgres enum public.user_role (column users.role) decides the portal and the RLS scope.

RLS helper functions

Policies call small SECURITY DEFINER helpers with row_security = off, which avoids recursive policy evaluation on users:

HelperReturns
current_user_role()The caller's user_role.
current_user_nursery_id()The caller's nursery.
is_xo_super_admin()Whether the caller is a platform admin.
rls_staff_manages_nursery(nursery_id)Whether the caller is an admin of that nursery (or its chain).
rls_staff_can_access_child(child_id)Whether the caller is staff allowed to see that child.
rls_authenticated_staff_sees_nursery(nursery_id)Whether any staff role in the nursery may read.
user_has_feature(key)Server-side feature check against role_features.

Typical policy shape: an _xo_all policy (is_xo_super_admin()), an _admin_all policy (admin role with matching nursery), a _staff_select policy, and a _parent_select policy limited to active rows of the parent's nursery or children.

The permission engine

1 · XO super admin?Full access, all actions
→
2 · DB matrixrole_features for users.role_id
→
3 · Static fallbacklib/permissions/matrix.ts
  • useFeatureActions(feature) in hooks/usePermissions.ts returns { allowed, requiresApproval, actions }, where actions is a set of view, create, update and delete.
  • usePermissionMatrix(roleId) loads role_features(feature_id, actions[], requires_approval) and caches it for 5 minutes.
  • A feature without view means no access. requires_approval corresponds to the "with approval" cells.
  • The static matrix maps roles to columns: chain_super_admin and branch_admin map to topManagement, and manager and teacher map to their own columns. A cell is full, none, with_approval or { requireDepartment }.
  • Navigation items declare a feature, and layouts hide items the user cannot view. RBAC settings pages are marked xoOnly.

End to end

Key flows

Flow A

Admission, payment and enrollment

  1. The parent signs up (parent-signup-complete) and fills the application from the nursery's parent_registration_templates.
  2. The parent picks a package and period. select_application_payment_package computes the subtotal from tuition_package_billing_periods, applies an active deal, and upserts the admission invoice.
  3. The parent declares a payment (submit_invoice_payment), which auto-submits the application for review.
  4. Finance confirms the attempt (confirm_invoice_payment_attempt). The payment is recorded and loyalty points are awarded.
  5. The admin approves (approve_application_enrollment). The child is created and a child_tuition_subscriptions row is opened with locked_price equal to the pre-discount subtotal.
Flow B

QR attendance and late billing

  1. Staff scan a QR. qr-verify and attendance_check_qr validate the token, the child and the tenant.
  2. record_attendance_check_in writes the record, an audit event (scanner, method, QR) and a parent notification.
  3. At pickup, record_attendance_check_out computes extra time from nursery_settings (from closing time or from check-in, rounding unit, grace).
  4. Extra time uses up extra-hours package hours first. The remainder is added to a daily or monthly invoice as a late item.
  5. The late-pickup-sweep bills children still checked in, up to the cap. admin_waive_late_charge reverses a charge.
Flow C

Recurring tuition billing

  1. Daily at 06:00, run_tuition_subscription_billing selects active subscriptions whose next billing date is due.
  2. _generate_tuition_invoice creates the invoice at locked_price for the subscription's period, and advances the next date.
  3. Parents are notified. Reminders follow through payment-reminders-daily.
Flow D

Deals and discounts

  1. A deal (deals) has a percentage or fixed value and an optional starts_at and ends_at, and is attached through deal_id on a package.
  2. Discount equals round(subtotal × value / 100, 2), or the fixed value, capped at the subtotal. It is written to the invoice line_items_json as subtotal, discount_amount and a negative line.
  3. First invoice only: enrollment locks the subscription to the subtotal, so recurring invoices are never discounted.
  4. The parent UI mirrors the same math (computePackageBillingQuote) and shows a live countdown to ends_at.

Defence in depth

Security

ConcernControl
Tenant isolationRLS on every tenant table, keyed on nursery_id and chain. npm run ops:cross-tenant signs in temporary test parents and checks that reads across tenants are denied.
Route accessProtectedRoute per portal, with role checks and redirects to /unauthorized. Navigation is filtered by feature. The UI is a convenience; RLS is the guarantee.
Privileged functionsSECURITY DEFINER with a pinned search_path and explicit caller checks. EXECUTE is revoked from anon and authenticated on internal and cron functions.
PaymentsSingle server path per action, with row locks, balance checks and idempotency keys. Parents cannot create attempts on another family's invoice or above the balance.
AuditAttendance events (scanner, method, QR), payment attempts with confirm or reject history, role_assignments_log and user_role_changes.
Media and documentsPrivate storage buckets served through short-lived signed URLs, media approval before parents see items, per-child visibility (media_children, media_visibility).
SecretsService-role and provider keys only in Edge Function secrets. The frontend only receives the anon/publishable key.
RealtimeOnly tables with RLS are published, so Realtime never streams rows a subscriber could not read.
AIAssistant actions are drafts that the user confirms, with safety rules (aiSafety), per-user rate limiting (aiRateLimit) and an opt-out.
ResiliencePer-tenant export (tenant-export), docs/backup-and-recovery.md, docs/incident-runbook.md and npm run ops:integrity.

Deployment

  1. Database: apply migrations with supabase db push (or --db-url against the pooler). The command applies, in order, every local migration missing from supabase_migrations.schema_migrations.
  2. Edge functions: supabase functions deploy <name>, with secrets set in the dashboard.
  3. Frontend: Vercel builds with vite build. vercel.json rewrites every path to index.html for client-side routing.
  4. Verify: run typecheck and lint, check the PostgREST schema cache picked up new relations, and smoke-test each portal.
Ship schema and code together

The frontend assumes the matching migrations are live. Deploying UI code before db push causes errors such as missing tables or columns.

Known technical debt

Generated database types are behind

tsc -b reports errors in several files (for example the course, roles, positions and features hooks) because src/types/database.ts predates newer tables. Regenerate the types with supabase gen types and remove the as never casts.

Untranslated strings

Some newer admin screens (deals, package editors, filter bars) use hard-coded English labels. Move them to locales/en.json and ar.json.

Native selects in older dialogs

The hours-package dialog still uses native <select> elements. Migrate them to FilterMenu for a consistent look.

Design doc drift

docs/rbac-roles-positions-features.md is marked "not implemented", but the RBAC tables, pages and per-action grants are live, and the matrix in code differs from the doc's table. Update the doc.

Lint baseline

The repository has pre-existing ESLint errors (for example react-refresh in components/ui/dialog.tsx and impure Date.now calls during render). Fix them, then enforce lint in CI.

Migration discipline

Several migrations were once left unapplied on the hosted database. Add a CI or deploy check that compares supabase migration list local and remote before each frontend release.
